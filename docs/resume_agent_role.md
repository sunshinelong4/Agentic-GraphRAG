## 2. 简历 bullet（按投递方向选 4–5 条）

### 必选（体现 Agent 工程能力）

- 基于 **LangGraph** 将单趟 RAG 重构为 **ReAct 式 Agent**：实现
  `plan → tools → assess → plan`（补检索）与 `verify → rewrite`（改问题）**双循环**，
  含工具名/参数双白名单、三层规划降级链、轮数与重试上限，保证任意异常下都有工具可执行。

- 设计**可计算的引用校验机制**替代"用另一个 LLM 当裁判"：校验答案中每个数字与实体
  是否出现在检索证据中，**引用可验证率达 1.000（14 题零未接地项）**，
  在垂直领域杜绝数值编造；不通过则自动改写查询重试。

- 建立 **LLM 用量与成本归因体系**（按节点统计调用次数/token/耗时），
  据此定位到多轮检索**过度触发**问题（14 题中 11 题补检索却无召回收益），
  加入零成本前置门控后：**单题延迟 16.2s → 9.0s（−44%）、单题 token 7,839 → 4,261（−46%）**，
  而多跳/聚合召回与引用可验证率**完全不变**。

### 强烈建议（体现 RAG 与知识工程深度）

- 在后端实现**知识图谱存储与多跳检索**（实体别名归并、带预算的 BFS 子图扩展、
  关系链枚举、最短路径、**Louvain 社区发现 + 模块度评估**），零外部图数据库依赖；
  并实现 LLM 驱动的**三元组抽取**，以"实体锚定白名单 + 证据必须为原文子串 +
  关系词规范化 + 共现降级"四道约束抑制幻觉。

- 构建**可复现的检索评测框架**（14 题 / 22 语料块，含干扰项与跨块问题），
  以 `single_chunk_ceiling` 给出"任何切块检索方案的理论上限"：
  **多跳问题上图检索召回 0.900 vs 关键词 BM25 0.567 vs 真实向量检索 0.500**，
  跨块问题"证据全部召回" 6/10 vs 4/10 vs 3/10，用数据证明
  **语义相似 ≠ 能拼出关系路径**。

- 补齐 **286 个离线单元/集成测试**（无 API Key 即可全量运行、约 2.5 秒），
  通过依赖注入（FakeLLM + FakeVectorStore）使 Agent 全闭环
  （含多轮工具调用、反思重试、三层降级）可被确定性断言。

### 可选（体现工程严谨性）

- 修复既有代码中的**向量库 metadata `eval()` 反序列化注入风险**（改 `json.loads` +
  schema 校验）、**`.env` 相对路径导致密钥读为空**的配置缺陷，并补齐缺失的
  `.env.example` 与评测隔离（独立 Chroma 集合，避免污染业务知识库）。

- 实现 **SSE 流式协议**（`sources → graph → assess → chunk → verification → retry → usage → done`），
  与既有接口向后兼容，前端可逐轮展示检索进展。

## 4. 面试问答（每条都对应代码里的具体实现）

**Q：你这个 Agent 是怎么工作的？**
两个循环。`plan → tools → assess → plan` 负责补检索：第 0 轮按问题选工具，
之后把已获证据的摘要交给模型判断还缺什么。`verify → rewrite` 负责改问题：
引用校验发现答案里有数字或实体在证据里找不到，就改写查询重试。两个循环职责不同，
混在一起讲会显得没想清楚。

**Q：一轮查几个工具？多轮会不会很贵？**
一轮可以并行调用多个工具（向量 + 图局部）。多轮默认上限 3 轮。
贵不贵我用数据回答：初版只要"有没用过的工具"就请判官复核，结果 14 题里 11 题都补检索、
平均 2.29 轮、单题延迟 16.2 秒，但召回相比单轮**没有提升**。
加了零成本门控（只在证据 < 400 字符或聚合型问题时才请判官）之后，
单题延迟降到 9.0 秒、token 降到 4,261，**关键指标一个没掉**。

**Q：为什么要做成本追踪？**
因为上面那个优化问题只靠"感觉慢"是发现不了的。我按节点归因 token 和耗时，
一看就知道判官和续查规划调用次数异常偏高，才定位到过度触发。

**Q：引用校验为什么不用 LLM 打分？**
LLM 打分不可复现、要花钱、还会引入新的幻觉。我做的是**可计算**的接地性检查：
答案里的数字（带 %、带小数、或长度 ≥ 2 位）和实体名是否都出现在检索证据里。
确定性、零成本、可复现，所以它能直接当评测指标用。

**Q：为什么需要知识图谱？向量检索不够吗？**
我实测过。多跳题上真实的 Chroma + DashScope Embedding 只有 0.500，
比关键词 BM25（0.567）还低，而图检索 0.900。原因是"语义相似的块"不等于
"能拼出关系路径的块" —— 跨块事实在向量空间里不会因为语义相关而自动靠近。
典型例子：药名在 ck-6、研制方在 ck-11，而 ck-11 只写"该 ARNI 类药物"，
词面上根本匹配不到药名。

**Q：那你这个图谱一定更好吗？**
不。细节和数值查找上切块检索是 1.000、图检索 0.750 —— `38%` 这类数值不是图谱实体。
而且真实的向量检索在细节题上也是 1.000。所以正确结论是**互补而非替代**，
最优配置是混合（0.982）。

**Q：关系抽取怎么防幻觉？**
四道约束：端点在已知实体白名单内且必须出现在本段文本里；证据必须是原文子串，
否则用包含头实体的句子兜底并下调置信度；关系词长度与格式受限；
只有 LLM **没有产出**（报错/空响应/不可解析）时才降级为共现边。
最后这条边界很重要 —— 如果"被约束拦下"也触发降级，就等于检测到幻觉后
立刻用兜底策略把噪声塞回来。

**Q：抽取质量能保证吗？**
不能保证，我如实说：同一段文本、`temperature=0`，两次调用抽出的三元组数量和内容
都可能不同（一次 4 条、一次 3 条），并可能漏掉关键边。
好消息是检索对图谱不完整有鲁棒性（查询里出现的实体都会成为种子做多跳扩展），
所以瓶颈在**抽取的完整性与一致性**，不在图算法。改进方向是多轮抽取取并集 + 共识过滤。

**Q：社区发现为什么用 Louvain？**
因为第一版我用标签传播（LPA），在"两个三角簇 + 一条桥边"这种图上会一路传播、
塌缩成一个巨型社区，模块度算出正好 0.0。换成模块度优化的 Louvain 局部移动后
同一张图得到 Q ≈ 0.36，两个簇正确切开。

**Q：没有网络/没有 API Key 时能测吗？**
能。369 个用例全部离线，2.9 秒跑完。关键是 `RelationExtractor` 和 `GraphRAGAgent`
的 `llm` 与 `vector_store` 都是**注入**的，所以四道约束、多轮循环、反思重试、
三层降级都能用 FakeLLM 确定性断言。这也是可测试性反过来影响设计的一个例子。
