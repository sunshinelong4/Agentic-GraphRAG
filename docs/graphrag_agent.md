# Agentic-GraphRAG 设计与实现说明

本文档是项目的技术说明，也可以直接当作面试讲稿使用。
每一节都遵循同一个结构：**改造前是什么样 → 为什么不够用 → 怎么改 → 怎么验证**。

---

## 0. 一句话概括

把"抽取式向量 RAG"升级为"图谱增强 + Agent 化问答"：
后端真正持有知识图谱（实体 / 关系 / 社区），检索同时支持**多跳遍历**与**社区摘要**，
问答环节由 **LangGraph** 编排成"规划 → 工具 → 生成 → 引用校验 → 改写重试"的闭环，
并用可复现的评测量化了增量（含不利结论）。

---

## 1. 改造前的状态（必须先讲清楚，否则后面全是空话）

项目原名叫 Agentic-GraphRAG，但代码现状（我接手时）是：

| 宣称 | 实际 |
|---|---|
| 知识图谱 | "图谱"只存在于**前端**。`KnowledgeGraph.tsx` 的 `generateRelationshipsFromItems()` 用硬编码规则拼边：<br>`if 人物 and 机构: relations.push({type: "属于"})`。任意一个"人物"会连上任意一个"机构"，不管原文里有没有关系。既不持久化，也不参与检索。 |
| 图检索 | 不存在。问答走的是纯向量余弦相似度。 |
| Agent | 不存在。`QAAgent.answer()` 是一趟 `retrieve → stuff → generate` 的直线流程。 |

这些不是"还不够完善"，而是**名不副实**。所以第一阶段的工作是先把话说实，
再逐条兑现。

## 2. 后端知识图谱（`graph_store.py`）

### 2.1 数据模型

```
Mention        实体在原文中的一次出现（doc_id + 字符区间）—— 溯源的最小单位
GraphEntity    规范化后的实体；不同写法归并到同一节点
GraphRelation  有向关系 source -> target，携带原文证据与置信度
```

三个设计决策值得说明：

**① entity_id 直接用规范化后的实体名，而不是 UUID。**
代价是不够规范（真实系统应有别名表 + 稳定 ID），收益是**可读可调试**：
打开 `knowledge_graph_store.json` 就能看懂图里有什么。对一个需要被讲解、被审查的项目，
可读性比规范性更值钱。

**② 实体名规范化是图谱质量的第一道关。**
`《王者荣耀》` / `王者荣耀` / `王者荣耀 `（尾随空格）必须归并成一个节点，否则图谱会被
同一实体的不同写法撕碎，度数虚高、社区发现失真。规则：NFKC 全角转半角 → 剥离
书名号/引号/括号 → 折叠空白 → ASCII 小写。

**③ 拒绝悬空端点是硬约束。**
关系的任一端点若不在已知实体集合内，直接丢弃。这是防"LLM 编造实体"的第一道闸门。

### 2.2 多跳检索：为什么必须是"跳"而不是"相似"

```python
store.neighbors("张建国", hops=1)   # {'扩张型心肌病', '北京协和医院'}
store.neighbors("张建国", hops=3)   # 含 '诺华'
```

`subgraph()` 用 BFS 扩展，带**节点预算**（默认 30）：热门实体 2 跳可能带出几百个节点，
全塞给 LLM 会爆上下文并稀释相关性。同一层内按度数降序保留（优先图上的枢纽实体），
并如实返回 `truncated` 标记 —— 让 LLM 知道"你看到的不是全貌"。

`relation_chains()` 把路径渲染成可读文本，这是"图 → LLM 上下文"的关键一步：

```
张建国(患者) --[服用]--> 沙库巴曲缬沙坦钠片(药物) --[属于]--> ARNI(药物类别) --[研制]--> 诺华(机构)
```

### 2.3 社区发现：一次真实的算法返工

第一版我用**标签传播（LPA）**（简单、20 行）。在"两个三角簇 + 一条桥边"的图上，
LPA 一路把标签传播过去、最终塌缩成**一个巨型社区**，模块度算出正好 `0.0`。
这是 LPA 的已知缺陷。

改用**模块度优化的 Louvain 局部移动**后，同一张图得到 `Q ≈ 0.36`，两个簇被正确切开。
增益公式（无向图，边权 1）：

```
把孤立节点 i 并入社区 C 的模块度增益：
    ΔQ = k_i,in / m  -  Σ_tot · k_i / (2m²)
```

每个节点依次尝试"留在原社区 / 并入邻居社区 / 自己单飞"，取增益最大者，
直到一轮无节点移动。平局取字典序最小的社区 id，保证**结果可复现**（否则评测数字每次不同）。

诚实标注：只实现了 Louvain 的**第一层**（未做图聚合递归）。中小图上效果接近完整 Louvain，
超大图应换 Leiden。

## 3. 关系抽取（`relation_extractor.py`）

### 3.1 四道防幻觉约束

LLM 抽关系天然会幻觉。这里不是"祈祷它别胡说"，而是四道可验证的闸门：

| 约束 | 做法 | 拦截什么 |
|---|---|---|
| **① 实体锚定** | 把已知实体列表喂进提示词，要求端点**必须**从中选取；抽完再校验端点确实在本段文本里出现 | LLM 编造不存在的新实体 |
| **② 证据必填** | 每条关系必须给出原文证据片段且必须是**原文子串**；不满足则用"包含头实体的那句话"兜底，并**下调置信度** | 关系被无中生有 |
| **③ 关系词规范** | 去空白与标点、限制长度 12 字、拒绝纯符号 | LLM 把一整句话当关系名 |
| **④ 共现降级** | 仅当 LLM **没有产出**时，退化为"同段落共现"的低置信度（0.35）边 | 一次 API 抖动导致空图谱 |

### 3.2 约束 ④ 的触发条件：一个由测试发现的真实设计缺陷

第一版的逻辑是"只要校验后为空就降级"。这导致：

```
LLM 幻觉 → 约束成功拦下 → 立刻补共现边 → 防幻觉机制被自己的兜底策略绕过
```

正确语义必须区分两种情况：

- LLM **报错 / 空响应 / 输出不可解析** → 没产出 → 可以降级（保证图不空）
- LLM **给了候选但被约束全部拦下** → 有产出 → **不降级**（约束生效，尊重结果）

这个边界是靠 `TestFallbackBoundary` 这三个反向用例固定下来的。

### 3.3 省 token：段落级预筛

只处理**至少含 2 个已知实体**的段落 —— 只有一个实体的段落不可能产出关系。
长文档上通常能跳过 70%+ 的段落。这不是微优化，而是让长文档抽取在成本上可行。

## 4. Agentic 问答（`agent_qa.py`）

### 4.1 图结构

```
plan ──► tools ──► generate ──► verify ─┬─(校验不通过且未超次数)─► rewrite ─┐
  ▲                                     │                                   │
  └─────────────────────────────────────┴─(通过 / 超次数 / 元信息问题)──► END
```

工具由 LangGraph 的 `ToolNode` 执行 —— 它负责把 `tool_calls` 派发到对应工具、
把结果包成 `ToolMessage`、处理参数校验与异常。这正是"工具调用"这一抽象的价值。

四个工具：`vector_search` / `graph_search` / `graph_global_search` / `kb_meta`。

### 4.2 路由：三层降级

1. **启发式（零成本、确定性）**：元信息问题 → 只查元数据；聚合问题 → 社区摘要 + 向量；
   其余 → 向量 + 图局部。
2. **LLM 复核**：启发式给出默认后，可用 LLM 重新决策（实测确实会改变选择）。
3. **失败回退**：LLM 路由抛错、或返回了白名单外的工具名 → 回退启发式，
   并把 `decided_by` 与 `router_error` 记进 trace。

第 3 层不是形式主义：模型编造工具名会让 `ToolNode` 直接报错，
所以 `_parse_tool_choice` 做了**工具名白名单过滤**。

### 4.3 引用校验：不依赖另一个 LLM 当裁判

RAG 最常见的失败不是"检索不到"，而是"检索到了但模型自己编了数字"。
垂直领域（医疗/法律/金融）里一个编造的数值就是事故。

`verify_citations()` 做**可计算**的接地性检查：

- 检查答案里的**数字**（带 `%`、带小数、或长度 ≥ 2 位）是否都出现在证据里
- 检查答案里提到的**图谱实体名**是否都出现在证据里

返回 `grounded_ratio`、未接地清单、是否通过。优点是**确定性、零成本、可复现** ——
所以它能直接当评测指标用，而不是每次跑出不同分数的"LLM 打分"。

判定阈值（默认 0.85）不通过 → 触发改写重试。

### 4.4 反思循环的两个边界（也都是测试发现的）

**边界一：`kb_meta` 问题不该重试。**
元信息问题的答案来自知识库统计，与检索质量无关，改写查询不可能改善它。
第一版会让它重试，结果第二轮路由被改成向量+图检索，**上报给调用方的 `route` 与实际不符**。
现在 `_after_verify` 显式排除。

**边界二：`route` 必须累计，`current_tools` 只反映本轮。**
重试会换工具。若只保留最后一轮，上报的 `route` 就漏掉了前面真正跑过的检索。
但重试决策又必须只看本轮。于是拆成两个字段。

**顺带修掉的问题：改写结果没有任何校验。**
改写节点的输出会**直接变成下一轮的检索输入**，脏输入污染整条链路。
实测中模型返回过"改写后的查询：xxx"这种带前缀的、以及整段拒答文字。
现在 `_sanitize_rewrite` 会去前缀/去引号/限长 120 字/拒绝拒答类开头，
不通过就退回确定性改写。

### 4.5 ReAct 式多轮工具调用

初版 Agent 每轮只做一次工具调用（虽然一轮内可并行调用多个工具），没有"看着结果再决定"
的能力。改造后的图结构：

```
plan ─► tools ─► assess ─┬─(证据不足，换工具补查)─► plan
                         └─(证据够用 / 到轮数上限)─► generate ─► verify ─┬─► rewrite ─► plan
                                                                        └─► END
```

**两个循环职责不同，不要混为一谈**：

| 循环 | 解决什么 | 触发条件 |
|---|---|---|
| `assess → plan` | **检索没拿到东西** | 本轮全部检索为空；或证据薄；或聚合型问题 |
| `verify → rewrite` | **检索到了但答案编造了** | 引用可验证率低于阈值 |

**多轮规划分两种情形**：
- 第 0 轮：只看问题，启发式打底 + LLM 复核
- 第 N>0 轮：把**已获证据的摘要**交给模型（`_digest_evidence`，每块截断 220 字符），
  让它判断还缺什么。摘要必须压缩 —— 这两次调用只是判断"缺什么"，
  不需要读全文，否则辅助调用的 token 会逼近答案生成本身，而产出只是一个工具名。

**证据必须累积不能覆盖**（这是最隐蔽的坑）：如果第二轮覆盖第一轮，
第一轮召回的跨块关系链会被第二轮的社区摘要冲掉，**多轮反而比单轮更差**。

**规划失败降级链**（保证永远有工具可执行，绝不出现"零工具")：

```
模型给的工具名非法/为空
    └─► 默认组合（向量 + 图）中没用过的
            └─► 其它没用过的工具
                    └─► 实在没得选，重复默认组合
```

另外还有一层：单轮内所有工具**全部返回空**时，自动换未用过的工具再查一轮。

### 4.6 过度触发：一次靠计量数据完成的调优

多轮上线后实测发现它**过度触发**：

| 指标 | 初版（无门控） | 加门控后 | 变化 |
|---|---|---|---|
| 平均工具轮数 | 2.29 | **1.5** | −34% |
| 触发多轮补检索的题数 | 11 / 14 | **4 / 14** | −64% |
| 单题 LLM 调用 | 4.57 | **3.14** | −31% |
| 单题 token | 7,839 | **4,261** | −46% |
| 单题延迟 | 16,150 ms | **9,033 ms** | −44% |
| 判官调用次数 | 18 | **6** | −67% |
| 多跳召回 / 聚合召回 | 0.900 / 0.950 | **0.900 / 0.950** | 不变 |
| 引用可验证率 | 1.000 | **1.000** | 不变 |

根因：**LLM 判官天然倾向于"再查一点更保险"**，对本来证据充足的问题也判不足，
于是 14 题里有 11 题都补检索，而召回没有任何提升。

修法是一道**零成本前置门控** `_needs_assessment()`：只在两种零成本可判的情况下才请判官：

1. **证据偏薄**（当前轮证据总量 < 400 字符）—— 说明召回质量确实成问题
2. **聚合型问题**（"涉及哪些/一共有几个"）—— 这类问题需要**完整清单**，
   部分样本就算内容很多也依然是错的，值得复核

其余情况直接生成。这把"多轮"从默认路径变回了兜底路径 —— 那才是它该待的位置。

**这件事的意义超出了这个项目本身**：如果没有按节点归因的 token 与延迟计量，
这个过度触发问题只能靠"感觉慢"来发现，而"感觉"没法支撑任何优化决策。
这就是为什么 Agent 系统必须自带计量。

### 4.7 成本与用量追踪（`llm_usage.py`）

三个必须能回答的问题：**每问一次花多少钱？延迟耗在哪一步？改了提示词后 token 有没有翻倍？**

设计取舍：

- **优先用 API 返回的真实 usage，拿不到才估算。** 兼容
  `usage_metadata`（LangChain 标准）与 `response_metadata["token_usage"]`（OpenAI 原生）两种格式；
  流式响应通常不返回 usage，此时按估算记录并**标记 `estimated=True`** ——
  估算值必须能被识别出来，否则指标会悄悄失真。
- **不引入 tiktoken**：它的 `get_encoding()` 首次调用要联网下载词表（离线环境直接失败），
  而且它是 OpenAI 的切分方式、对 DeepSeek 本来就不精确。既然都不精确，
  就用"中日韩字符 1 字符 ≈ 1 token，其余 4 字符 ≈ 1 token"的透明近似。
- **不硬编码价格**：未配置单价时 `cost` 返回 `None` 并标记 `cost_configured=False`。
  给 0 会被误读成"免费"。宁可少一个数字，也不要一个假数字。
- **按节点归因**：`by_node` 分别统计 `route` / `plan_followup` / `assess` / `generate` /
  `rewrite` 的调用次数与 token。没有归因就不知道钱花在哪，也就无从优化。
- **失败也要记账**：调用抛异常时同样记一条（带 `error`），否则失败请求的成本被静默吞掉。

一次请求一个追踪器实例（存在 state 里），不做成 Agent 成员变量 ——
FastAPI 的同步路由跑在线程池里，成员变量会让并发请求的用量互相污染。

## 5. 两处工程妥协（主动讲出来，比被问出来强）

### 5.1 流式路径为什么手写编排

LangGraph 的 token 级流式（`stream_mode="messages"`）需要全程 async。
本项目的向量库与 FastAPI 路由都是同步的，为它做 async 改造收益不划算。

所以 `answer_stream()` 按**同样的节点顺序**手动编排，节点实现完全复用。
但**不能复用 `ToolNode`**：LangGraph 1.x 的 `ToolNode` 在 `invoke` 时会从运行配置里取
runtime，脱离已编译图单独调用会抛 `ValueError: Missing required config key 'N/A'`。
于是另写了 `_execute_tools()` 做图外派发，并多加了一层**参数白名单过滤**
（与工具名白名单同类防御：模型可能编造参数名，直接透传会让工具抛 TypeError）。

### 5.2 关系抽取非确定性 —— 当前真正的瓶颈

实测（`python -m evaluation.live_smoke`，真实 DeepSeek，`temperature=0`）：

| 运行 | 抽出的关系数 | 是否含 `张建国-服用->药` |
|---|---|---|
| 第 1 次 | 4 | 是 |
| 第 2 次 | 3 | **否** |

第二次漏了那条边，于是 `张建国 → 诺华` 的最短路径不存在。
**但 Agent 依然答对了** —— 因为查询里同时出现了"张建国"和药名，实体链接把两个节点都
设成了种子，2 跳子图仍然够到"诺华"。

**结论：多跳检索对"图谱不完整"具备鲁棒性；瓶颈在抽取的完整性与一致性，不在图算法。**

改进方向（也是最有价值的下一步）：
- 对同一文档做多轮抽取取并集
- 按多次抽取的一致性过滤（Microsoft GraphRAG 的 gleaning + 共识思路）
- 跨段共指消解，让"该药""该患者"稳定绑定到实体

同时这解释了**为什么评测用人工标注的固定图谱**：
用现场抽出来的图做基准，每次数据都不一样，数字无法复现。

## 6. 评测：怎么做到"零成本拿到核心数字"

### 6.1 关键洞察

GraphRAG 的价值体现在**检索阶段**（能不能召回跨块证据），而检索**不需要 LLM**。
所以最核心的对比可以纯离线、零成本、秒级、可复现地跑出来。

### 6.2 指标设计

| 指标 | 定义 | 作用 |
|---|---|---|
| `evidence_recall` | 期望关键词出现在检索证据中的比例 | 检索阶段端到端指标；证据没召回，LLM 再强也是零 |
| `single_chunk_ceiling` | 遍历所有单块，取"单块作为证据"时的最高召回 | **任何切块方案的理论上限**，用来判断一道题是否原理上需要跨块 |
| `on_cross_chunk` | 仅统计 `ceiling < 1` 的问题 | 最能体现实质差别的一组 |
| `fully_solved` | 跨块题里证据被**全部**召回的数量 | 比平均召回更能反映"能不能真的答对" |

### 6.3 一次诚实的返工

第一版评测跑出来 `chunk_bm25` 在多跳题上是 **1.000**，且没有一个问题达到"切块无解"。
看起来 GraphRAG 毫无价值。排查后发现是**我的评测数据设计有问题**：

1. **事实堆在同一块**：把"药由诺华研发，属于 ARNI"写在一个块里，
   一个块就装下了全部答案，多跳题退化成单块题。
2. **语料太小**：8 个块取 top-5，几乎等于全取，任何检索器都能蒙中。
3. **干扰块意外泄题**：指南块恰好同时列出了 ARNI 与 SGLT2抑制剂，
   把本该跨块的类名聚合题变成了单块题。

返工：事实原子化（一块一事实）+ 语料扩到 22 块（含 8 个干扰块）+ top_k 收到 3 +
说明书用**类名指代**（"该 ARNI 类药物由诺华研制"，不重复药名 —— 真实文档就是这么写的）。

这些约束现在都由 `tests/test_evaluation.py::TestFixtureIntegrity` 固化，
防止将来又把评测数据改"简单"了。

### 6.4 最终结果

**离线检索评测**（14 题，22 块，top-3）：

### 6.5 三组结论（全部固化成回归测试）

| 结论 | 数据 |
|---|---|
| 多跳题上图检索显著更优 | vs 切块 0.900 vs 0.567；vs **真实向量** 0.900 vs 0.500 |
| 跨块题"全对"更多 | 6/10（图）vs 4/10（BM25）vs 3/10（向量） |
| 两路**互补而非替代** | 混合 0.982（BM25+图）/ 0.946（向量+图）均为同组最高 |
| 垂直领域防编造 | 引用可验证率 **1.000**，14 题零未接地项 |
| **反向结论：细节/数值题切块检索更好** | 1.000 vs 0.750 |

最后一条必须主动讲。`38%` 这类数值不是图谱实体，图检索天生不该在这里取胜。
把它包装成"全面碾压"会在面试中被一句话问穿：
**"那你们的图检索对什么样的查询反而更差？"**

还有一个值得强调的发现：**真实的 Embedding 向量检索在多跳题上（0.500）
甚至略逊于关键词 BM25（0.567）**。这打破了一个常见直觉 ——
"语义相似的块"并不等于"能拼出关系路径的块"。
跨块事实在向量空间里不会因为语义相关而自动靠近，这是 GraphRAG 存在的根本理由。

延迟方面：内存图 0.2ms，真实向量检索 135ms（主要耗在 Embedding API 调用上），
Agent 端到端 4.7s（主要耗在 LLM 生成上）。三者量级差异要如实报告，
不能拿 0.2ms 去和端到端比。

## 7. 测试策略

286 个用例，**全部离线**，无 API Key 也能跑，耗时约 2.5 秒。

| 测试文件 | 关注点 |
|---|---|
| `test_graph_store.py` | 规范化、别名归并、悬空端点拒绝、多跳可达性、社区发现、持久化往返 |
| `test_relation_extractor.py` | 四道约束、脏 JSON 解析、降级边界、省 token 行为（注入 FakeLLM） |
| `test_graph_retriever.py` | 局部/全局检索、弱证据标注、截断提示、问题分流 |
| `test_agent_qa.py` | 完整 Agent 闭环、反思重试、三层路由降级、SSE 事件序列（FakeLLM + FakeVectorStore） |
| `test_api_routes.py` | FastAPI 集成：路由注册（走 OpenAPI 契约）、SSE 协议、落盘与重载 |
| `test_evaluation.py` | 评测数据完整性 + **结论回归** |

两个让测试成为可能的**设计决策**（可测试性反过来影响设计）：

1. **`RelationExtractor` 的 `llm` 是注入的**，不是构造函数里 `new` 出来的。
   否则"四道约束是否生效"就只能靠真调 API 验证 —— 慢、贵、不确定。
2. **`GraphRAGAgent` 的 `llm` 与 `vector_store` 都是注入的**，
   所以整条 Agent 闭环（含反思重试）能在毫秒级被断言。

最有价值的一组用例是 `TestMultiHopReachability`：它断言
"3 跳内必须能到达诺华"且"1 跳够不到" —— 用对照把"多跳是必要的，不是炫技"这件事固定下来。

## 8. 面试问答准备

**Q: 你这算 GraphRAG 吗？**
原版不算：图只在前端由硬编码规则拼出来，不参与检索。我补齐了三块 ——
后端图谱存储、LLM 驱动的三元组抽取（替换硬编码）、多跳与社区两条检索路径，
并且用 A/B 评测量化了增量。多跳题 0.900 vs 0.567。

**Q: 为什么用图检索而不是纯向量？**
举评测里的具体反例。"张建国服用的药是哪家公司研发的" —— 药名在 ck-6、研制方在 ck-11，
而且 ck-11 只写"该 ARNI 类药物"，词面上根本匹配不到药名。向量检索原理上召不回完整证据。

**Q: 那图检索什么时候更差？**
数值/细节查找。评测里 detail 类切块 1.000 vs 图 0.750。`38%` 不是图谱实体。

**Q: 你们和向量 RAG 比过吗？**
比过，而且接的是真实 Chroma + DashScope Embedding，不是词面替代品。
多跳题上向量检索只有 **0.500**，比关键词 BM25（0.567）还低，而图检索是 **0.900**。
跨块题"证据全对"向量只有 3/10，图是 6/10。
结论是：语义相似 ≠ 能拼出关系路径。

**Q: 关系抽取怎么保证不幻觉？**
四道约束：实体锚定白名单 + 证据必须是原文子串（不满足则用句子兜底并降置信度）+
关系词格式限制 + 只在 LLM 无产出时才降级共现。
另外实测发现抽取并不完全可复现，这是当前的主要瓶颈，改进方向是多轮抽取取并集。

**Q: 你的引用校验凭什么可信？**
不依赖另一个 LLM 当裁判，而是可计算的接地性检查：答案里的数字与实体名是否都出现在
检索到的证据里。确定性、零成本、可复现，所以能直接当评测指标。

**Q: 项目里最难的点？**
两个。一是社区发现从 LPA 换成 Louvain（LPA 在桥接图上塌缩成单一社区，模块度算出 0.0）。
二是评测返工 —— 第一版基线拿满分，排查发现是自己的语料设计把多跳题退化成了单块题。
后者更值钱：它说明指标对了不代表评测对了。
